# Setup, host, Git, and runtime boundaries

## Bootstrap and setup

The project skill cannot be selected before it exists. Start from a downloaded kit checkout with the standard-library CLI:

```text
python "PATH_TO_KIT/.agents/skills/spec-team/scripts/setup.py" --project "PROJECT_PATH" --apply
```

The CLI contract is `--project PATH`, optional `--apply`, and repeatable `--skills-root PATH`. Without `--apply` it reports proposed writes/conflicts only. Planned/successful runs use `SPEC_TEAM_SETUP_PLANNED` / `SPEC_TEAM_SETUP_APPLIED` and exit 0; conflict or invalid input exits 1 with a short field/path error. Bootstrap installs missing project-local kit entry files/profiles/templates additively. Add a small managed pointer to an existing `AGENTS.md` without replacing its contents. After the entry skill is available, `setup` checks/install missing pinned skill files from included archives. Setup is idempotent, no-overwrite, and project-local by default. It may reuse discoverable project/user/plugin skills, but report observed path/version/provenance and don't claim a present copy matches the pin without comparing. A difference is a conflict for manual reconciliation, never an automatic upgrade. If a required skill is absent or conflicting, affected role readiness remains incomplete until resolved.

The only managed families are Superpowers, UI/UX Pro Max, and Ponytail. Read the lock manifest for exact archive checksums, revisions, and skill-folder mappings. Keep license notices with their archived files. Setup validates archive checksum and member type/path/size before extraction; rejects traversal, absolute, duplicate/case-colliding, link, reparse, and redirected destinations; and doesn't execute scripts/hooks. No third-party package, global install/config write, telemetry, credential copy, auth/login, Git initialization/configuration, external resource creation, or product work. Existing AGENTS, settings, memory, and third-party skills are retained; conflicting managed files are reported. Preserve pre-existing files if an apply partially fails.

When UI/UX Pro Max is applicable, resolve the real discovered skill directory and invoke its bundled `scripts/search.py` directly with Python. For example, use `python "<actual-skill-dir>/scripts/search.py" "<product> <industry> <direction>" --design-system -p "<Project>"` for a design system or a focused query with `--domain ux --max-results 1`. Pixel can query the approved stack with `--stack <approved-stack>`. Do not assume a Claude-specific root/environment variable exists; the kit's project copy is under its configured `.agents/skills` destination. Keep its scripts and data intact, use only relevant results, and do not alter the upstream copy to fix a host-path assumption.

## Host and permission preflight

Product runtime/package installation is a later tracked task governed by [environment preparation](environment.md), after package approval and real Linear issue readback. The bootstrap restrictions above apply to the kit installer; they do not prohibit approved product tasks from using native stack tools. Planning inspection remains read-only.

Supported intent is Codex or ChatGPT Desktop local Work/Codex where that host can access the project and expose local skills, native dispatch, required model/effort, authenticated Linear/Git tools, and safe filesystem operations. Confirm the actual host capabilities at use time. Ordinary Chat is not assumed to access local files, execute a script, select a role model, or dispatch a local worker. Skill-picker visibility, model routing, and enforcement require live observation; copied config alone proves none of them.

Record `runtime` host/dispatch and each capability as `{available, evidence}` for `native_dispatch`, `role_selection`, `model_selection`, `permission_scoping`, `linear`, `git_provider`, and `worktrees`. Null means unknown. Permission evidence names parent/tool/identity/resource restrictions and distinguishes enforced controls from instructions/unknowns. A role profile, prompt, task/thread, or worktree is not by itself a sandbox or authorization boundary. Do not set ineffective role `sandbox_mode` or `approval_policy`; don't change parent/global settings. If an action needs an unavailable hard boundary, withhold that action and continue unrelated authorized work where safe.

Always request the exact profile model and reasoning effort. Report observed selection separately; if the host cannot select or verify the requested setting, stop that dispatch. Do not silently substitute, create an unrelated user chat as a worker, or claim role-name prompting changed the parent model. Sol Extra high is the ceiling. Escalate only after a diagnosed high-risk/difficult issue and return routine work to the role default.

## Settings, records, and controller ownership

Project settings are inert `.spec-team/project.json` with schema version 1. Keep only real provider IDs, credential-free remote URL, actual base/merge strategy, explicit capability observations, and configured validation commands; null fields remain unknown. Reject credential-named fields (`api_key`, `access_token`, `refresh_token`, `password`, `secret`) and control/newline injection in attribution fields. Credentials come from authenticated tools, never the file.

Use ignored `.spec-team/run.json`, `owner.json`, and `reports/` under the retained primary controller root, not the removable implementation worktree. Kit source and controller may initially differ. Pass both roots to validation/dispatch until the kit is merged/retained. The root binds the actual repository, run UUID, claim, and approved phase IDs. Do not copy a different run's receipts or controller. Relay alone updates the execution record.

Run state uses the documented schema version 1 and valid states: `idea`, `spec_review` (compatibility only), `planning`, `plan_review`, `setup`, `implementing`, `in_review`, `awaiting_acceptance`, `merging`, `cleanup`, `complete`, `stopping`, `stopped`, `blocked`. Inert identity fields are null, phase list empty, and no state is marked passed. Active mutation requires actual repository/root/run/claim identity, current owner claim, approved spec/plan hashes, approved phase IDs, and an assigned phase. Write records through a complete temporary sibling file and replace after success so failed writes preserve the previous receipt.

Approval entries independently retain `{path, sha256, evidence}`. Paths stay within the retained repository; SHA-256 is over exact immutable saved bytes. Both may cite one owner message approving the complete package. Changes invalidate the affected receipt. Do not use historical memory or a copied text example as approval.

The current phase records `id`, `issue_ids`, `worktrees`, `head`, `base_sha`, `tree_sha`, `review`, `acceptance`, `pr`, `merge`, `cleanup`, and `dispatches`. Worktree entries record `{path, branch, base_sha, owner, status}` where status is `active`, `reviewing`, `retained`, `removal_pending`, or `removed`; state detached checkouts honestly. Review is `{head, base_sha, tree_sha, verdict, evidence}` with `PASS`, `CHANGES REQUIRED`, or `INCOMPLETE`. Acceptance is `{method, head, base_sha, tree_sha, result, evidence}` with method `manual`/`automated`/null and result `pending`/`pass`/`fail`. Manual acceptance evidence comes from the owner; review PASS can coexist with pending acceptance. PR snapshot is `{url, head, base, base_sha}`. Merge is `{status, request_id, commit, evidence}` where only actual `merged` plus provider evidence/commit proves it. Cleanup is `{status, evidence}` (`pending`, `preserved`, `complete`, `failed`). Dispatch records contain `{role, requested_model, requested_effort, observed_model, observed_effort, worker_id, retries, usage}`; unobserved fields stay null. Completed reports contain `{id, path, merge_commit, cleanup_status}`.

Active workflow states need bound identity, approved documents, phase IDs, and assigned phase. `in_review` and `awaiting_acceptance` need a known full candidate/base/tree; the latter additionally needs matching review PASS. `merging` needs stop false, matching review and acceptance pass, and matching PR snapshot. Pending/queued/unknown merge never authorizes cleanup or Done. `cleanup` requires actual verified merge and snapshot. `complete` requires exactly one retained merged report for every approved phase and cleanup complete. Empty arrays cannot prove completion. `stopping`, `stopped`, and `blocked` preserve unresolved history and gates.

Create a local exclusive controller claim; never use check-then-overwrite, timeout-based takeover, PID-only takeover, or `--force`. A second app/session stays read-only. An explicit owner-requested handoff is the only routine transfer: stop new mutations, reconcile in-flight work, checkpoint, release, and have the named destination claim the same root/run and re-read live state. Recover an unavailable controller only after verifying it is quiescent.

## Worktrees, review, merge, and cleanup

Use native managed worktrees when supported; otherwise use verified Git worktrees. Inspect current branch, WIP, registrations, attachments, and existing work before creation. Default to one worktree per meaningful phase and sequential writers; at most one active writer per worktree. Independent writers need separate branches/worktrees and an explicit owned-file/resource agreement. Separate checkouts do not isolate ports, databases, fixtures, deployments, migrations, or hardware. Preserve the owner's primary checkout.

Lens independently reviews the integrated candidate. Keep review separate from acceptance. At phase boundary, ask the owner to select manual acceptance or Lens automated acceptance. Do not merge until required review PASS, selected acceptance pass, exact same repository/head/base/tree, and repository-required checks/protections all match. A provider request that was accepted, queued, timed out, or returned unknown is not a verified merge. Reconcile it before retrying. Use an expected-head guard and verified current-base integration protection; refresh checks/review/acceptance if the integrated base/tree changes. If the provider cannot enforce required protections, preserve the reviewed work and report merge unavailable.

Reuse existing appropriate required CI. Add the smallest provider-native check running the existing tests and structural validator only when needed for the approved server-enforced merge policy and the provider is actually selected. Verify the source, exact check name, accepted snapshot and successful result; skipped/neutral/canceled is not success. Preserve existing rules and never bypass a required check. No target repo/provider or branch protection is configured by this portable kit.

Use the configured human Git author and include exactly one `Co-authored-by: Codex <codex@openai.com>` trailer on Codex-authored commits, preserving existing coauthors. Keep the trailer in squash messages and verify resulting commit metadata. Attribution does not grant provider access. A commit footer does not prove GitHub rendered a contributor; observe linked authors and the actual Contributors display when that pilot is authorized.

Before cleanup, verify the merged target tree equals the accepted tree, then inventory tracked/untracked/needed ignored files, unmerged commits, active registrations, and owned processes. Keep the controller root and records, Git administrative/common dirs, primary WIP, and unrelated resources. Resolve canonical paths and Windows junction/symlink/reparse redirection. Reject controller/ancestor/protected overlap. Remove/archive only the exact dedicated registered worktree using its native lifecycle and verify both deregistration and folder state; never use raw recursive deletion as fallback. If blocked, preserve data and report cleanup pending/failed. Keep the source usable in a retained checkout before removing its delivery worktree. No remote branch/repository deletion or deployment is implied.

## PR and evidence

Use the repository's PR template and, if installed, the implementation skill's delivery template resolved at runtime. Lead with the concrete problem and resulting behavior. Include consequential implementation choices, spec/issue links, actual validation/environment, relevant risks, and remaining gates; omit empty sections and activity chronology. Record delivery base/head/CI/merge evidence separately. Never imply a local check proves hosted, production, UI interaction, accessibility, field performance, device, or physical acceptance.

# Workflow and authority

## Stages and approval

`start IDEA` inspects project evidence and the existing run first. Spark separates confirmed requirements, unknowns, and suggestions; it asks focused questions when an answer could change behavior or architecture. Muse contributes only relevant audience, flow, state, visual-system, responsive, and accessibility decisions. Atlas prepares a detailed technical plan using verified repository paths and identifies proposals separately. Prepare the full product specification and technical plan together for one owner review. Do not create a separate specification approval gate before the technical plan.

The package review covers product goals/users/flows/scope/non-goals/acceptance, consequential assumptions, architecture and rationale, stack, data and API contracts, authentication/permissions, security, UX/accessibility, implementation order/ownership, tasks/phases, tests, deployment/recovery, case coverage, quality profile, and remaining tradeoffs. The owner approves the complete package before Relay writes project/ticket data or starts product implementation. Do not request an approval again when an unambiguous current owner approval is already recorded. Finalize both documents before review; progress belongs in Linear/run evidence, not edits to approved bytes.

`approve` requires exactly one current package presented for decision with both project-relative paths and SHA-256 values. The human must explicitly approve that package. Record `approvals.spec` and `approvals.plan` separately as `{path, sha256, evidence}` and point both `evidence` values to the same actual owner message. Hash exact saved bytes; do not normalize. Missing, stale, changed, unsafe, or ambiguous documents remain unapproved. `spec_review` may be read for compatibility, but is not a required separate user gate. Approval does not authorize arbitrary setup, production work, a review verdict, acceptance, or deployment.

After approval, Relay continues into Linear setup and tracked implementation only when the relevant host/tool, account, repository, ownership, and permission requirements are observed. Unavailable setup remains an explicit blocker; save a local draft where useful without claiming it is a remote resource. Material changes return to the owner with a revised spec/plan before affected work continues. Routine choices within the approved plan do not need repeated approval.

Inspect product environment requirements read-only during planning. After the complete package is approved and real Linear tasks are created/reconciled and read back, follow [environment preparation](environment.md): Relay coordinates, Pixel or Forge prepares the assigned worktree, and Lens checks relevant evidence. Include it in the first coherent task unless substantial independent setup merits its own issue. Verify compatible dependencies and service identities, install as the approved recipe requires, and complete required smoke checks before dependent feature work. Saved observations and reusable sign-in never replace current approval, ownership or permissions. Kit `setup` retains its skill-installation scope.

## Role handoffs

| Role | Owns | Routing and boundary |
| --- | --- | --- |
| Spark | Product discovery, scope, user journeys, requirements, observable acceptance | Use `$brainstorming` when it improves discovery. Clarifies rather than deciding consequential owner choices. |
| Atlas | Architecture, stack fit, contracts, data/security approach, detailed plan | Use `$writing-plans` after the product package is ready; use `/ponytail full` for economical choices. Keep unverified paths and recipes marked proposed. |
| Relay | Run ownership, bootstrap, Linear writes/status, dispatch, evidence and resume | One active controller. Use `$using-git-worktrees` and `$subagent-driven-development` when available; `$executing-plans` for an explicitly sequential execution. Never impersonate a model or Linear account. |
| Muse | Product-specific UX flows, content hierarchy, visual references/tokens/components, interaction states, accessibility | Use `$ui-ux-pro-max` for applicable design work. Cite why references fit; don't make every product look alike. |
| Pixel | Frontend implementation, integration, focused implementation checks | Use the installed `$linear-issue-implement ISSUE-ID` when available, `/ponytail full`, and relevant UI/UX, TDD, or debugging guidance. Return evidence to Relay; do not write Linear status. |
| Forge | Backend/data/permissions/migrations/integrations and focused checks | Use the installed `$linear-issue-implement ISSUE-ID` when available, `/ponytail full`, and applicable test/debug guidance. Do not load UI guidance for backend-only work. |
| Lens | Independent spec/code review and selected automated phase acceptance | Use `$linear-pr-qa ISSUE-ID` and `$verification-before-completion` when available. Read-only: no implementation fixes, Linear writes, merge, deployment, or acceptance fabrication. |
| Dock | Integration, combined checks, authorized merge, local cleanup | Use `$finishing-a-development-branch`, `$verification-before-completion`, and `/ponytail full` where applicable. Work under Relay's run and report facts; it does not become another controller. |

Optional `linear-issue-implement` and `linear-pr-qa` may be reused if installed; only Superpowers, UI/UX Pro Max, and Ponytail are kit-managed families. Use skills only when relevant. Each dispatched profile uses its explicit default model/effort; the host must support it. Sol Extra high is the ceiling. Escalate only after diagnosing high-risk or difficult work, record the reason, and return routine follow-up to its default. Credentials/tool failures are access problems, not model-selection reasons.

## Tasks, phases, and evidence

Group related steps into one coherent issue and meaningful phase. Split for dependency, independent ownership, size, or genuine isolation, not to maximize agent count. Implementers run focused checks during work. Lens reviews one combined phase delivery independently against the approved plan, connected code, risks, and actual evidence. Return fixes to their original implementer where practical; rerun changed checks and re-review the changed scope. No new review per small edit.

At phase readiness, identify repository, candidate head, target-base commit, and integrated tree. Lens review and phase acceptance are separate. Relay asks the owner to choose manual acceptance or Lens automated acceptance. Silence, a build, a PR, or a review PASS is not acceptance. Manual evidence comes from the owner. Automated acceptance states actual commands/scenarios/environment; unavailable hosted, visual, device, assistive-technology, field, or hardware gates stay unverified. If acceptance is pending, preserve an existing code-review PASS as PASS but do not merge. Continue to the next approved phase automatically after review, selected acceptance, and required repository checks pass, unless the owner stops.

Review/acceptance must bind the same repository, head, base SHA, and integrated tree. Any changed snapshot invalidates merge readiness and affected checks. Lens independently judges scenario answers; the controller cannot grade itself into a PASS. Required failures or missing evidence block affected acceptance. A missing required hard permission boundary blocks that action, regardless of role instructions or score.

After two equivalent failed fix attempts without new evidence, require a revised diagnosis and route the question to the right role before another equivalent attempt. This is a diagnostic checkpoint, not an extra approval or a hard work budget. Record starting failures separately from regressions, elapsed delivery time, rework cause, findings, model/effort observations, and available usage; unknown metrics remain unavailable.

## Cases and product quality

Spark identifies normal user journeys plus relevant edge and credible worst cases before package approval. Atlas adds technical boundary, permission, integration, data, and recovery behavior. Muse adds relevant loading, empty, denied, error, responsive, and accessibility states. Use stable case IDs in the spec and technical plan; Relay links relevant IDs in existing issue acceptance/validation sections; the phase report records result, evidence, and environment. Include applicable cases rather than quotas. Critical missing behavior is resolved before dependent implementation. A build does not prove a journey or recovery.

The technical plan has one project-quality profile. For applicable criteria, record target/scope, rationale/risk, verification/environment, owner/phase, and planned/unverified evidence status. Cover critical journeys; security/agent authority; design/content/interaction; responsive/accessibility environments; stack/contracts/maintainability; performance/load/recovery. N/A requires a reason. No score can offset a required correctness/security failure.

Security records assurance target/version and applicability/exclusions, trust boundaries/data flows, sensitive-data handling, role/resource/operation permissions, and relevant abuse cases. Production apps with accounts/private data target applicable OWASP ASVS Level 2 requirements. Higher-impact behavior needs an explicit escalation assessment and named human decision owner, including whether qualified human review is required. The actual owner is a project input; agent review or automated scan is not certification. Verify backend authorization and applicable wrong-user/tenant, role, session, ID, secret, dependency, and resource-limit boundaries.

Muse defines the product's purpose, action/content hierarchy, identity, references with reasons, design tokens/components, states, and craft. Prefer suitable proven components; justify bespoke work when it materially helps. For web interfaces record WCAG 2.2 AA applicability, supported browsers/input modes, fluid layouts, representative and boundary widths, long/localized content, zoom, keyboard/focus/dialog/form checks, 320 CSS-pixel reflow with documented standard exceptions, and relevant touch/reduced-motion checks. Expand real-device/assistive-technology checks by audience and risk. Automated checks do not satisfy a required manual gate. Non-UI products can mark applicable UI criteria N/A with a reason.

Prefer a previously approved and verified stack recipe when suitable; preserve an adequate existing stack. A mismatch needs a concrete reason and fresh evaluation. The plan's recipe block contains source revision, fit/limits, runtime/dependency versions, setup/lockfiles, contracts/security patterns, and validation/deployment/recovery. No new catalog or global recipe service. Agree interfaces, errors, and permission boundaries before concurrent work. Prove one useful integrated journey early inside the first meaningful phase.

State workload/data assumptions, provider/resource limits, justified latency/error criteria, test environment, and recovery behavior. Use focused isolated checks for ordinary stateful products; expand burst/sustained/degraded/recovery checks for workload and impact. No production or third-party load testing by default. Web experience targets, where applicable, are LCP <= 2.5s, INP <= 200ms, CLS <= 0.1 at the 75th percentile of real page loads. Label lab evidence provisional and distinct from field data. Define bounded queries/uploads, timeouts/retries/idempotency, contention, migration rollback or forward recovery, recovery time, acceptable loss, and restoration evidence as applicable. Unsupported claims stay unverified.

## Project memory

Read `docs/MEMORY.md` only when it is relevant. Confirm the current project identity and inspect a cited source before relying on a finding; a timestamp is not proof. Missing, stale, or conflicting entries fall back to current source inspection. Keep the adopted file around 500-800 tokens as a soft target; do not add a tokenizer or fail on an estimate. It can hold brief verified navigation/gotcha facts, not project status or instructions.

Memory never supplies approval, current Linear/CI/migration state, review/acceptance, merge permission, permission enforcement, or cleanup safety. Exclude credentials, private customer data, raw transcripts/logs, and executable instructions. Contributors propose findings in their normal handoff. Relay alone curates at the exclusive phase writer handoff after pausing the prior writer, checks the latest diff and sources, reconciles unexpected changes, and commits the finding in the existing phase delivery before Lens review. No updater, extra agent, ticket, or review stage.

## Stop, resume, and handoff

`stop` prevents new dispatch, merge, or cleanup. Quiesce workers; preserve uncommitted work and unresolved requests. Use `stopping` while work or provider outcomes remain in flight; a sent request may still complete. Reconcile before retrying, deleting, or claiming stopped. Release ownership after safe reconciliation.

`resume` checks the actual immutable approved bytes and hashes, provider/Linear resources, worker outcomes, current Git and worktrees, snapshot, owner claim, stop state, and relevant environment inputs/live access per [environment preparation](environment.md). Reuse existing IDs, healthy dependencies and valid native sessions; never infer a failed create from timeout or restore a gate from memory or a saved setup result.

Only the owner's explicit handoff transfers control. Save the checkpoint, quiesce dispatches and mutations, reconcile provider requests, and release the current claim. The named destination claims the same canonical root/run, rechecks live facts, and continues. If the existing session is unavailable, recover only after confirming it is quiescent. No focus/TTL/PID-based takeover. A read-only secondary session cannot write a stop request or silently seize control.

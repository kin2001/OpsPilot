# Inventory guardrails and shortage recovery (26C)

The additive `supabase/migrations/20261025000100_inventory_guardrails.sql` extends the accepted 26A/26B commands. `src/contracts/inventory.ts`, the shared schema, client methods, generated public database types and `get_job_parts` projection remain unchanged. Existing membership, assignment, AAL2, role, exact-decimal, version, rate and durable request identity checks remain authoritative. No new public RPC or direct-table access is introduced.

## Discrepancies

`private.stock_consistent` compares every affected part/location's signed immutable ledger with on-hand, and active reservation sums with reserved. It also compares each reservation's cumulative issued/returned quantities with immutable linked job movements, and rejects missing/misbound movement links and unit disagreement. The union of balances, ledger and reservations detects missing balance rows; a pair without either stock history or balance is an ordinary zero-stock absence. It does not treat a cached issued total as authoritative evidence of consumption.

New receipt/adjustment/reserve/release/issue/return commands reject an affected discrepant pair with the existing `CONFLICT` error. Cancellation performs the same check before releasing unused allocations. Multi-line failures roll back every stock change, WO version, notice, audit and receipt. Consistent other locations remain usable. The unchanged job-parts read reports `reconciliation_state=discrepancy` if any requested part is inconsistent. It does not expose unrelated stock details.

Current authorization precedes durable receipt replay. An authorized identical replay of a successful historical command still returns its original envelope even after a later discrepancy; it makes no new stock or notification change. Revoked access cannot retrieve it. Changed payloads still conflict. The tenant admission lock and accepted asset → work-order → sorted part/location lock order remain unchanged.

## Low-stock cycles

Thresholds apply independently to each existing part/location balance, using exact `available <= reorder_threshold`. A different shelf cannot hide low stock at this shelf. `private.stock_low_state` retains one latch/event identity per balance. A new low cycle emits `low_stock` notices with `source_id=balance.id`, one event ID shared by the authorized active owner/manager/supervisor/inventory recipients. Existing notification uniqueness and recipient RLS retain deduplication and read ownership. Technicians/other tenants receive no low-stock notice.

Evaluate final command state after all ledger/reservation writes, avoiding the temporary zero balance inserted during a first receipt. A first balance ending low emits once; ending above threshold emits none. Further changes while low, including issue (which reduces reserved and on-hand equally), do not repeat. An open cycle retains the threshold that originally made that location low; only authoritative availability above that captured threshold rearms it. Archiving or disabling a threshold suppresses new notices without clearing an open cycle. Lowering then raising the configured threshold also cannot rearm an unresolved cycle. Genuine above-cycle-threshold quantity recovery can rearm while notices are suppressed; re-enabling/reactivating then emits only on a subsequent low observation. If no cycle is open, threshold edits evaluate the current threshold normally. New members do not receive historical events retroactively. Upgrade seeds current latches without sending historical notices. Discrepant locations cannot produce a trustworthy new threshold event.

## Explicit blocked work

A user's existing `transition_work_order` command remains the only way to block/resume. When an explicit block has current requested shortages, `private.capture_parts_block` stores exact `parts_shortages` in that immutable work-order event's `changes`, alongside the supplied reason. It emits recipient-scoped `blocked_parts` notices (`source_id=work_order.id`, event ID of the block). Replaying the block does not repeat facts/notices. Existing job/asset read permissions apply when following a source; a notice grants no record access. UI link/rendering support belongs to 26D.

Coordinator resume (`blocked → scheduled/in_progress`) still requires current owner/manager/supervisor authority, current version, and explicit reason. It rejects remaining shortages with `INVALID_TRANSITION` and inconsistent requested stock with `CONFLICT`. The frozen shortage formula counts reserved stock as fulfilling demand: reservation without issue may permit explicit resume. Receipt/reserve/issue never resumes, completes, reviews, resolves holds or releases an asset automatically. Review and independent human release retain their existing separate checks.

## Recovery and evidence

Recover forward using an authorized consistent snapshot, preserving private cycle state, original command receipts, inventory/job ledger links, shortage block event snapshots, recipient notices/read state and current Auth/member decisions. Stop affected writes and investigate a discrepancy; no application RPC silently rebuilds balances, deletes history or uses a physical adjustment to conceal inconsistent facts. Human investigation determines an authorized forward repair; this issue introduces no general repair/admin bypass. A normal failed transaction rolls back automatically. A migration anchor drift aborts the migration transaction rather than guessing a predecessor definition. No destructive down migration is supplied.

`supabase/tests/database/014_inventory_guardrails.test.sql` covers exact equality/rearming, discrepancy rejection, missing balance/link faults and private-role boundaries. `tests/integration/job-parts.test.ts` adds isolated shortage→block→receipt→issue→explicit resume→review→release, reserved-but-unissued resume, per-location recipient dedupe, denied access/replay/cancellation and unaffected-location scenarios. Existing multi-line, 20-contender, decimal, revocation, cancellation and reopen tests remain required. Upgrade rehearsal includes a populated 26B snapshot and original receipt/read preservation; recovery verifies private cycle state and low-stock recipient facts after restore. Local structural checks supplement these observable database tests; they do not prove SQL execution. Full job-owned Linux PR CI must run upgrade/reset/native types/SQL/Edge/integration/browser/recovery/schema/cleanup. Qualified human security, inventory business-process and private-pilot acceptance remain separate.

# Inspection submission and private evidence

POR-32 / slice 25D provides initial submissions; POR-33 / slice 25E adds immutable corrections and failure episodes. Inspection UI follows in 25F.

## Commands and reads

All commands use the existing authenticated `{ organization_id, request_id, expected_version? }` context and `{ data, version, request_id }` envelope. Callers keep the same request ID and exact payload after uncertain acknowledgement. A different payload under that identity returns `CONFLICT`. Authorization is rechecked before replay. The database records actual actors; callers cannot supply inspector or publisher attribution.

| RPC | Contract |
| --- | --- |
| `publish_inspection_template(ctx, fields)` | Operations coordinator publishes `title` and 1–100 uniquely identified items `{ id, label, required, safety_relevant, evidence_required }`. Existing template ID requires its current version; publication adds an immutable revision. |
| `assign_inspection(ctx, asset_id, template_revision_id, inspector_id, due_on?)` | Coordinator pins an immutable assignment to an existing revision and eligible active inspector. New assignments on archived assets are denied. |
| `submit_inspection(ctx, assignment_id, template_revision_id, results)` | Only the actual assigned active eligible actor submits once. Results have unique `item_id`, `outcome: pass\|fail\|not_applicable`, `evidence_ids`, optional `reason` and `remarks`. Fail/N/A require remarks, N/A additionally requires a reason. All required items must be present; configured evidence must be ready and belong to this assignment. |
| `correct_inspection(ctx, assignment_id, template_revision_id, supersedes_id, correction_reason, results)` | Assigned active eligible inspector appends a correction with the pinned revision, latest submission ID and required current submission `expected_version`. Reason is 1-2000 trimmed characters; full results use original validation/evidence rules. Actual actor/time are server supplied. |
| `reserve_inspection_attachment(ctx, assignment_id, name, media_type, size)` | Assigned inspector reserves a bounded private image for initial submission or correction; existing 10-image assignment and organization byte quotas remain. Use existing `uploadPrivateImage` and `downloadPrivateImage` for bytes, or the existing attachment Edge POST/PUT/GET flow with `assignment_id` reservation. |
| `list_inspection_templates(organization_id, cursor?, page_size?)` | Eligible members read template headers, ordered by UUID. |
| `list_inspection_revisions(organization_id, template_id, cursor?, page_size?)` | Eligible members read immutable published revisions, ordered by revision number. |
| `list_inspection_assignments(organization_id, cursor?, page_size?)` | Coordinators read organization assignments; technicians read only their own, ordered by UUID. |
| `get_inspection(organization_id, assignment_id)` | Returns `{ assignment, revision, submission, history, episodes, episode_links, holds }` with the same assignment authorization. Submission is null before first submit, otherwise the latest immutable result. History is ordered by version with `supersedes_id`, `correction_reason`, actual `inspector_id` and time. Episode links identify `{ submission_id, item_id, episode_id }` for each failed historical result, including reused remedies. Holds expose separate resolution/release facts. |

Lists default to 25 and reject sizes outside 1–100. UUID continuation is the last returned ID, revision continuation the last returned revision; null means no further page. An assignment permits at most 100 immutable submissions; history is bounded at 100 and episodes, failed-result links and holds at 10,000 (100 items times 100 submissions). At the limit further corrections/reservations return `RATE_LIMITED` and pending finalizations return `INVALID_TRANSITION`. Original receipts lacking new nullable lineage fields remain readable. Shared strict Zod schemas and the typed client freeze these DTOs. Attachments add optional nullable `inspection_assignment_id` to keep existing persisted responses readable.

## Safety and authorization

Submission, first failure episode, Submitted corrective request, source-linked safety hold, audit and notification effects commit together. Each failed item creates one episode/request; only safety-relevant failures create holds. A coordinator explicitly converts each request into a work order. Submission never completes repair or releases an asset. Original labels/rules, evidence IDs, results, inspector and time remain immutable when later templates publish.

Submission uses the existing organization then asset lock order used by release. A safety failure on an already archived asset still creates a fresh unresolved hold and changes availability to Out of Service. A release racing that failure either observes the hold or precedes the failure that invalidates availability.

Inspection evidence uses the existing private repair-evidence bucket, bounded image structural validation and service-only finalization. Reservation/finalization remain available for corrections within those bounds; all metadata, Edge and Storage reads recheck current role, membership, account and assignment. Revoked actors lose access even when retaining an old session. No signed download URL or broad asset-read permission grants inspection evidence access. Existing image and organization quotas remain intact.

Inspection hold disposition remains an explicit authorized human action. An active linked repair blocks disposition; Completed repairs require their current independent review. Release retains evidence, AAL2, blocking work and unresolved hold gates. Immutable current/former repair participants of a linked inspection remedy are excluded while its hold remains unreleased, including after disposition; prior released scope is not a lifetime ban. Software checks do not replace the approved human safety procedure.

## Correction episodes and forward recovery (25E)

Corrections require the latest predecessor ID and version. Identical request/payload retries return the committed receipt even after a later correction; changed payload conflicts. Distinct request IDs racing on one predecessor produce one successor and one CONFLICT. Authorization precedes replay. Original results, evidence associations, authors, reasons and predecessor links remain immutable. New evidence never rewrites prior evidence.

Failure reuses its current episode when its request is Draft/Submitted/Returned, or Converted with a work order outside Completed/Canceled. After Rejected/Withdrawn, Canceled or Completed work, failure creates one new predecessor-linked episode and Submitted request; safety items add an unresolved hold atomically. Coordinator conversion stays explicit. Old work/request status remains intact. Pass only appends facts: old unresolved holds still need separate authorized disposition. Existing immutable participant guards exclude current/former remedy participants for every unreleased hold, including resolved-but-unreleased holds; released prior scope is not a lifetime ban.

Migration `20261024000400_inspection_corrections.sql` replaces assignment-wide submission uniqueness with assignment/version and single-successor constraints, adds nullable lineage/reason with a same-assignment predecessor foreign key, and extends commands/reads. Existing rows remain version 1 with null lineage; durable receipt bytes remain unchanged. No new service-role mutation authority is granted. Recovery uses a reviewed forward correction or authorized restore, never deleting history or reopening old work. Stop affected writes if lineage/hold integrity is uncertain.

`011_inspection_corrections.test.sql` covers reason/version/identity/role validation, immutable facts, active reuse, terminal-request succession, unchanged Pass holds and read links. Integration adds isolated ordinary fixtures for distinct-identity contention, same-identity retries, changed payload, wrong actor/tenant/revoked actor, fresh private correction evidence, Converted-active reuse and Rejected/Withdrawn/Canceled/Completed-and-released successors. Existing release/participant gates remain covered. Populated 25D-to-25E upgrade verifies old receipt bytes and new lineage; recovery verifies original/correction replay and old/new episode/hold links. These service scenarios require actual isolated CI execution; local checks alone do not establish service PASS or human safety acceptance.

A safety failure reusing an active remedy checks all holds with that episode's inspection `source_id`. If its old hold was disposed or released, correction appends one fresh unresolved source-linked hold and refreshes availability atomically; it never rewrites old disposition/release facts or duplicates the request/episode. `episode.hold_id` retains the initial hold; `holds` contains initial and renewed holds joined through `source_id`. Disposition and participant-release guards apply to every such row. Retry retains one renewed effect. Each renewal requires a new submission, so existing 100-submission / 10,000-hold bounds remain.

Availability refresh runs only when this command inserts a new safety hold, including a renewed hold. Initial Pass/non-safety submissions and Pass corrections preserve existing availability and asset version; they neither release nor re-block a previously released asset.

# Grounded Assistant gateway (POR-41 / 27C)

The Assistant is disabled by default. Manual work orders, reporting and parts commands operate independently. This slice adds no UI or operational AI writes. Never render generated prose or retrieved notes as HTML.

## POR-42 client contract

Import `askAssistant`, `listAssistantConversations`, `getAssistantMessages`, and `deleteAssistantConversation` from `src/app/assistant-client.ts`; import schemas/types from `src/contracts/assistant.ts`. Preserve the user's manual input after every failure; never automatically retry a paid request. A repeated request ID returns `AI_REQUEST_REUSED`, including after a lost response. The user may inspect its saved conversation; a new explicit request uses a new identity and counts again.

`AssistantRequest` contains organization_id, request_id, optional conversation_id, mode, prompt (1–4,000 trimmed characters), and a typed query. Modes are `draft`, `priority`, `operations`, `asset_history`, and `daily_brief`. The seven query kinds are `blocked_work_orders`, `completed_work`, `overdue_work`, `awaiting_parts`, `asset_history`, `daily_metrics`, and `recurring_fault_counts`. All queries require a local calendar range `{from,to}` with exclusive end and at most 366 days. Only asset_history accepts/requires asset_id and accepts an optional category. Asset-history and daily-brief modes require their corresponding query kind. Blocked/overdue/parts queries describe current state; their supplied range bounds completion metrics, rather than pretending current state is a historical snapshot. Awaiting parts means recorded demand with outstanding shortage; counts describe jobs, not stock quantities.

The schema-v1 result returns answer, uncertainty, validated source_ids, nullable draft, run_id, conversation_id, retrieval, provider metadata and confirmation. DraftSuggestion is `{schema_version:1,title,reported_problem,category,suggested_priority,reasoning_summary,asset_candidates:[{id,label}]}`. Priority may be null when unknown. Priority mode provides a prose suggestion, always subject to human review. Model-generated suggestions are not database facts. Show uncertainty, retrieved_at, range and truncated. Display numeric values from retrieval.facts, rather than extracting arithmetic from generated prose. Its counts and recurring-fault groups are computed in PostgreSQL. `scope=current_authorized_work` denotes coordinator totals; `scope=retrieved_source_sample` denotes only the saved source sample for technician/inventory, so history can recheck every contributing record. Missing/incomplete evidence is not zero historical downtime, an inferred repair outcome or approval.

Only draft mode for owner/manager/supervisor returns confirmation.allowed=true. `confirmation={allowed,command:'create_work_order',request_id,requires_human_review:true}` is guidance for the ordinary work-order form. Human confirmation must select/review the asset, editable fields, priority and critical-priority reason, then use the existing `createWorkOrder` command and the same original request_id. Existing deterministic holds/escalation/authorization and command idempotency remain authoritative. The Assistant does not invoke this command and cannot approve, release equipment, modify inventory or grant membership. Technicians use their existing maintenance-request flow. Inventory receives only necessary awaiting-parts job context, with repair notes omitted.

History conversations have `{id,created_at}`. Messages are separate discriminated rows: user `{id,created_at,role:'user',prompt,result:null}` and assistant `{id,created_at,role:'assistant',prompt:null,result:AssistantResult}`. One request saves both rows transactionally. There are at most 50 conversations per user across organizations and 50 total messages per conversation (25 complete exchanges). Capacity for both rows is checked at admission and completion; no partial exchange is saved. Pages contain at most 25 records and a nullable next_cursor UUID. Conversations are newest first; messages are chronological with a stable timestamp/ID cursor. A page may split an exchange. Persist neither client cache nor responses across users/organizations; clear history on identity/organization changes.

Source IDs refer to current-authorized work orders; asset_candidates are validated against their retrieved asset IDs. Build source links using the application's ordinary work-order/asset routes and current authenticated reads. Missing/revoked resources become unavailable. History is owned by the current active member, requires the same role and current access to every saved retrieval source, and is hidden after membership/assignment revocation. Changing roles conservatively hides earlier conversations. Deletion requires current membership and own conversation, immediately removes active transcript rows, and cancels any in-flight save by removing its conversation reference. Minimal non-content run metadata remains for rate/replay accounting.

## Server boundary and operations

All tables are in the unexposed private schema, with no application/table grants. Caller RPCs perform current identity/tenant/role/resource checks; only service_role can execute assistant_finish, and it rechecks the saved actor, role, synthetic gate, lease and all sources before storing output. Fixed SQL retrieval never executes model-supplied SQL/tools. Retrieved notes are untrusted data. No previous transcript is sent to the provider and no cross-user cache exists. Ordinary logs contain no raw prompt, answer, note, provider key or provider response.

Transactional admission locks both organization and user. It durably counts failed/abandoned attempts: one active user request, five/user/rolling hour, fifty/organization/UTC day. A 60-second lease recovers an abandoned process; the Edge request budget is 30 seconds and its single provider call is capped at 20 seconds. Provider response tokens are capped at 2,000; retrieval is capped at 50 sources/20,000 serialized characters. Network/configuration/validation failures return fixed safe errors and no partial answer. A lost finish response may leave a saved exchange; history/replay identity must be inspected before another paid request.

The daily `opspilot-assistant-retention` database job removes up to 1,000 expired messages at 02:17 UTC. Every history read excludes content at or beyond 30 days from each message's creation even before cleanup. Conversation shells can be deleted by their owner. Monitor backlog and increase cleanup frequency only after an approved operational change if the bounded daily batch cannot keep up. Retained backups can contain deleted or expired content until their established backup-retention period expires; active deletion does not claim immediate erasure from old backups. Before reopening a restored service, reconcile current membership/assignments, post-snapshot deletion receipts and content expiry. The recovery rehearsal tests this with in-memory synthetic deletion IDs; it does not create a production deletion journal or prove hosted backup retention.

No migration enables AI for any existing organization. The private assistant_organizations gate is synthetic-only and has no client enablement RPC. The Edge deployment also requires ASSISTANT_ENABLED=true, ASSISTANT_SYNTHETIC_ENVIRONMENT=true, ASSISTANT_PROVIDER_KEY, and an explicitly pinned ASSISTANT_MODEL, plus existing server-only SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY and APP_ORIGIN. Never put provider/service keys in VITE variables or the client bundle. This task supplies no key, model, provider account, private-data approval or paid-call authorization. Synthetic tests use separate job-owned environments and fake fetch responses. Configuration flags are not proof that a provider's spending cap or private-data terms gate has been met. Provider account no-cost-overage controls and any live synthetic smoke remain external unverified gates. Real tenant AI remains disabled pending the actual owner-confirmed provider/privacy/retention/business gate and demonstrated tenant filtering.

The standard-fetch adapter uses Google's documented [generateContent REST endpoint](https://ai.google.dev/api/generate-content) with systemInstruction, JSON MIME/JSON schema output, maxOutputTokens, and no tools. Responses require one STOP candidate and actual modelVersion/optional responseId; schemas and every cited ID are validated again locally. [Structured output documentation](https://ai.google.dev/gemini-api/docs/structured-output) informs the request shape; no eligible live model is asserted by these docs or fixtures.

## Migration and recovery

20261025000400_assistant.sql is additive and preserves operational sources/receipts. It creates private gate/conversation/message/run tables, RPCs, restricted helpers and a bounded Cron cleanup job. The populated upgrade rehearsal checks unchanged operational facts and disabled AI after migration. Native generated-type equality, pgTAP, deployed Edge startup, concurrent RPC/service fixtures and full backup/restore rehearsal run in existing isolated Linux CI. Missing local Docker/psql/Deno is an unverified environment gate, never a PASS.

Recovery uses forward fixes, preserving operational receipts and ai_runs admissions. To stop new calls, disable the server kill switch and the affected synthetic organization gate; allow the bounded in-flight call to finish, or remove its conversation before restoring access. Do not delete admissions to bypass quotas. A reverted application release may leave the additive private schema safely disabled. Removing tables would discard history and rate receipts and is not an automatic rollback. Do not run this migration or modify settings on production/hosted resources under this task.

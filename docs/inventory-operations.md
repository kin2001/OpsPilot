# Inventory 26A contract and recovery

This slice adds catalog, locations, physical receipt/adjustment history and exact stock balances. Job requests, reservations, issues/returns, shortage notifications, reconciliation screens and inventory UI belong to subsequent slices. Purchasing, valuation and automatic procurement are excluded.

## Commands and authorization

Authenticated `owner` and `inventory` members call `save_part(ctx,fields)`, `save_stock_location(ctx,fields)`, `receive_stock(ctx,fields)` and `adjust_stock(ctx,fields)`. The strict shared schemas in `supabase/functions/_shared/inventory.ts` are re-exported through `src/contracts/inventory.ts`; `src/app/inventory-client.ts` is the typed consumer. No actor, tenant override or role claim belongs in `fields`.

`ctx` contains `organization_id`, a caller-retained UUID `request_id`, and `expected_version` for catalog updates only. Catalog creation omits `id` and expected version; update includes both. Each tenant has unique part/location codes. Part fields are `code`, `name`, `unit`, a decimal-string or null `reorder_threshold`, and optional boolean `archived`. Location fields are `code` and `name`. A part's unit may change before its first movement; afterward it is immutable. Code/name/threshold edits retain optimistic version checks and do not rewrite ledger units.

Archiving sets server `archived_at` while retaining catalog, balances, movements and receipts. Repeated archival preserves its original timestamp; omitting `archived` preserves current state, and explicit false reactivates the item under the same optimistic version/role checks. Bounded catalog reads include archived state/history. Fresh receipts against archived parts fail `INVALID_TRANSITION` atomically; an authorized identical replay of an earlier receipt remains valid. Authorized AAL2 physical adjustments and linked compensations remain available for historical correction after retirement. Archiving cannot change a historical unit or erase stock.

Receipt fields are `part_id`, `location_id`, `quantity`, `unit`, and optional `source` text. Adjustment adds `direction` (`in` or `out`), mandatory nonblank `reason`, and optional `correction_of` movement UUID. Adjustment requires the verified Auth `aal2` claim, including a receipt replay. Every command rechecks active, confirmed, nonbanned user membership and current role after acquiring the tenant lock, before reading a durable receipt. Role removal or membership revocation denies replays as well as new writes. Existing Auth access-token expiry/sign-out limits remain; no immediate global session revocation is claimed.

Corrections append a full opposite-direction movement of the predecessor's exact quantity, part, location and unit, with a reason and `correction_of`. Each predecessor may have one compensating successor. An unlinked adjustment records a physical count correction with its own reason. A compensation can itself be compensated by a new linked successor if that correction was mistaken; all prior facts remain. Outgoing adjustments cannot consume reserved stock or exceed available stock. No command edits or deletes a posted movement.

## Exact quantities, retries and reads

Quantities are unsigned decimal strings with at most eleven integer and three fractional digits (`numeric(14,3)`), maximum `99999999999.999`. Movements must be positive. Thresholds may be zero. No whitespace, sign, exponent, leading integer zero, JSON number or excess precision is accepted. The database validates the original JSON type/text before conversion; it never silently rounds an RPC quantity. Direction carries the ledger sign. Response quantities/thresholds/balances are decimal strings (stored scale three); the browser performs no floating-point stock arithmetic. Schema numeric fields in generated database types describe storage only; use these RPCs for exact transport.

The transaction serializes tenant mutations using the existing organization lock and locks the part/balance. Balance change, one immutable ledger row, business audit and durable receipt commit atomically. `available = on_hand - reserved`, with all three nonnegative and reserved no larger than on-hand. In 26A reserved remains zero through public commands. New reservations must preserve this boundary in 26B. The signed ledger sum equals on-hand for every part/location; read paging uses UUID order, not chronology.

On an uncertain acknowledgement, retain the original request ID and identical context/fields and explicitly retry. Identical replay returns the original envelope, without a second ledger/audit mutation or rate charge. Any payload change, including a different decimal spelling or action, conflicts. A fresh request ID represents a fresh command. The existing limits remain 60 commands per actor/minute and 5,000 per tenant/day; failed commands roll back, and receipts have no destructive automatic expiry. The API reports the existing domain errors (`VALIDATION`, `FORBIDDEN`, `UNAUTHENTICATED`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`, `INVALID_TRANSITION`, `DEPENDENCY_UNAVAILABLE`). Overdraw conflicts require an explicit availability refresh and corrected new request.

`list_inventory_parts`, `list_stock_locations`, `list_inventory_balances` and `list_inventory_movements` require `organization_id`, accept optional UUID `cursor` and `page_size` (default 25, maximum 100), and return `{items,next_cursor}`. Balances/movements accept optional same-tenant `part_id`/`location_id` filters. Current owner/manager/supervisor/inventory members may read these bounded views. Technician access to job-linked availability is deferred to 26B; technicians cannot read the tenant catalog/ledger here. Direct table reads/writes and private dispatchers are revoked from API roles, including service-role. RLS is enabled/forced, and public commands are granted only to authenticated users. Internal service keys do not supply an alternate stock command route.

## Migration and recovery

`20261024000500_inventory.sql` is additive to accepted inspection/maintenance history. No existing data is rewritten. Preserve the migration, catalog, balances, immutable movements, command receipts, audit history, current Auth/member decisions and configuration references in the approved encrypted recovery process. The isolated upgrade/recovery rehearsals now exercise exact stock and durable receipt replay, while preserving their existing job-owned loopback, permission, Auth, Storage and cleanup checks.

Recover forward: stop affected stock writes, restore an authorized consistent snapshot into an isolated verified target, reconcile current access decisions, verify ledger sum/balance/available equality, then check original request replay and changed-payload conflict before resuming. Do not rebuild balances by deleting movements or receipts. A posted business error uses an authorized AAL2 linked compensation; a failed transaction leaves no partial balance/ledger/receipt. No destructive down migration or hosted restore is authorized by this delivery.

Required evidence: local type/lint/unit/build/diff checks; isolated SQL authorization, twenty concurrent attempts against final stock, native schema generation/comparison, populated upgrade and consistent recovery in full CI. Local source projection of generated types is provisional until native CI matches. Missing local Docker/Auth/PostgreSQL services do not count as passed checks. Applicable ASVS 5 Level 2 trust boundaries remain; qualified human/security, business process and private-pilot gates are separate from synthetic CI and independent agent review.

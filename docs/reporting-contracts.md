# Deterministic report facts (POR-39 / 27A)

`get_report(ctx, kind, range, cursor={})` is a read-only authenticated RPC. `ctx` contains only `organization_id`; the database derives the actor from verified Auth claims and checks current active membership and Auth user eligibility on every call/page. Owner, manager and supervisor may read all six kinds. Inventory officers may read only `parts_consumption`. Technicians have no team-wide report access. Anonymous and service-role execution are revoked. Reports grant no direct table access and do not weaken command, MFA, tenant or stock permissions. Bulk export is a separate 27B boundary and must enforce its own current authorization/AAL2, row and time limits.

`range={from,to}` uses real ISO local dates and the organization's current timezone, converted once to UTC `[from,to)`. It must contain 1–366 calendar days. A DST day may contain 23 or 25 hours; a date-line zone may begin the UTC day before. PM uses its occurrence's pinned timezone/cutoff instead of recalculating due times from the organization's current zone. `cursor={after?:uuid,page_size?:integer}` defaults to 25 and permits 1–100 rows. Each fixed source orders by immutable UUID ascending, reads at most page size + 1, and returns `next_cursor={after,page_size}` only when another row exists. Cursors are continuation positions, not authorization or a snapshot token. Concurrent edits can change current facts between calls; `generated_at` identifies each evaluation. Changing filters starts a new read. A 15-second database statement timeout bounds each request; timeout/dependency failures require narrower filters or a later retry, never partial success.

Each envelope has `schema_version:1`, kind, original local range, UTC `from`/`to`, timezone, currency, generated timestamp, bounded items, next cursor and a server-calculated summary over the authorized full source, independent of page size. No caller SQL, grouping expressions, rates or formulas are accepted. `supabase/functions/_shared/reporting.ts` is the strict Zod allowlist re-exported by `src/contracts/reporting.ts`; `ReportFacts` is the shared typed retrieval contract for 27B/27C. It contains source identifiers and operational facts, without repair narratives, user email, credentials or private attachment paths. The Assistant must consume these deterministic facts without calculating replacement totals or widening access.

| Kind | Source rows and exact definition |
| --- | --- |
| `work_orders` | Source WOs created in range, currently completed with valid latest approval in range, or currently active WOs created before the exclusive end. Rows expose ID, number, asset, recorded category, current status, initial open, current valid approval and duration. Current active means open/scheduled/in_progress/blocked/awaiting_review; drafts are excluded from current counts. Blocked and pending approval are current statuses; overdue is active with due_at strictly before server now. These current counts are snapshots, not reconstructed historical statuses. |
| `asset_availability` | Recorded assets created before range end, with immutable `asset.availability_changed` events ordered by `(changes.occurred_at,id)`. Consecutive event boundaries form nonoverlapping state intervals per asset. Clip to asset creation, range and server now; sum unavailable active intervals once, including overlapping holds. Across assets the total is asset-seconds, not a wall-clock outage duration. Archived/inactive intervals contribute no downtime. Missing baseline or unverified initial/migration provenance makes `history_complete=false` and `downtime_seconds=null`. `known_downtime_seconds` is a clearly partial observed subtotal. Future availability remains unknown. Empty recorded asset sets have known zero downtime. |
| `pm_compliance` | Persisted generated occurrences with scheduled local date in range and pinned due cutoff at/before server now. Denominator includes every due eligible generated occurrence regardless of current WO state. Exclude canceled occurrences only when an immutable cancellation event has an explicit reason. Completion must remain current and have a valid latest approval strictly before the pinned exclusive cutoff; equality is late. Summary exposes eligible denominator, completed_on_time numerator, completion sample size and unknown completion count. A completed WO without a valid approval is unknown; any unknown completion or empty denominator gives null rate. `coverage=generated_occurrences`: ungenerated calendar backlog is outside recorded coverage; this does not claim overall calendar compliance. |
| `technician_assignments` | One row per tenant member, including retained inactive membership, with role/active flag and count of currently assigned (`unassigned_at is null`) active WOs. Completed, canceled and draft jobs contribute zero; former assignments contribute zero. A job assigned to two members counts once for each member, so the summary is assignment count, not distinct job count. This is current coordination workload, independent of selected date range, never a productivity score. |
| `parts_consumption` | Immutable issue/return movements in the UTC range, linked through job movement/reservation records. Expose only movement/job/part/location IDs, kind, unit, occurred_at and exact fixed-scale decimal strings. Issue is positive consumption; return is negative. `quantity_policy=net_by_part_and_unit` prohibits adding incompatible units/parts; summary reports movement count, not an invented global quantity or valuation. Reservations are not consumption; receipts/adjustments are excluded. |
| `maintenance_costs` | The accepted source schema has no entered cost or unit-cost field. Return an empty row set and `label=Entered maintenance-cost estimate`, `entered_estimate=null`, `coverage=unavailable`, `reason=entered_costs_not_recorded`, retaining known tenant currency. Missing input is not zero. No rate is inferred from labor minutes, stock quantity or model output; no accounting valuation is claimed. Future entered cost support needs an approved input contract. |

Current-completed means current status completed plus the latest immutable approved review for the current repair revision, ordered by `(created_at,id)`. Reopened jobs retain historical reviews but contribute no current completion. Duration is that approval minus initial open, including blocked time. Missing initial open or invalid chronology has no duration sample; average is null for no samples. The dashboard calls the same work-summary and availability helpers, preserving its existing response shape. Its last seven local-day availability points use the same occurred-at/provenance clock and leave unverified/future points unknown.

Work summaries also expose local-day `daily_completed` counts for the full selected range and recorded `recurring_faults` grouped by asset/category for initial opens in range, excluding drafts. These counts describe recorded jobs, not diagnoses. The first 100 groups use stable asset/category order; `recurring_faults_has_more` requires narrower filters/future bounded retrieval before claiming complete group coverage. Detailed WO facts remain cursor-paged. No model arithmetic is needed to draw the supplied completion trend or display category counts.

## Checks and recovery

The dedicated transactional pgTAP fixture owns synthetic identities/data and independently expects 3 current completions, 2 duration samples averaging 35,970 seconds, one 10,800-second unavailable interval despite overlapping state/holds, a missing-history null, PM numerator 1 / eligible 3 with exclusive cutoff, two active technician assignments, exact issue `0.300` and return `-0.100`, and unavailable cost null. Additional cases cover unknown approval, DST/date-line boundaries, 366/367 days, default/max pages, tenant/role/revocation/banned-user denials and restricted grants. HTTP integration owns a separate ordinary tenant and tests real Auth/RPC decoding, pagination and revocation. Local contract/client checks do not substitute for database execution.

This additive migration changes no authoritative WO, occurrence, audit, stock row, receipt or command. The populated-upgrade rehearsal hashes authoritative sources before/after migration and verifies all six envelopes. Recovery reuses the existing job-owned database/Auth/storage backup rehearsal, compares report source projections after restore, and checks that retained revocation still blocks report access. Availability known subtotals use observation time and are re-evaluated rather than incorrectly compared across wall-clock restore time. Native schema generation/comparison remains required in Linux loopback CI; the checked-in type change is the new RPC signature only.

On an interrupted migration inspect the actual migration state before retry. For a report defect, disable/withhold the consuming UI or forward-fix the read functions; do not delete histories, alter command receipts, rewrite posted stock, or manufacture old availability events. The previous dashboard definition is in migration `20261022000100_operations.sql`; restoring that definition is a reviewed forward migration if necessary, not a destructive database reset. Restore data only through the separately owned tested recovery procedure. Unavailable local database, integration, browser, upgrade/recovery and native-type checks remain unverified until the complete required CI passes.

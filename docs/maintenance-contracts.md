# Maintenance plan commands and preview

POR-29 implements plans, immutable revisions, protected date segments and bounded authorized reads. Generation, occurrences, work orders, native Cron and the Maintenance page are dependent POR-30/31 work. No scheduled execution is installed by this migration.

The shared Zod definitions are in `supabase/functions/_shared/maintenance.ts`, re-exported by `src/contracts/maintenance.ts`; `src/app/maintenance-client.ts` owns the typed client boundary. Database authorization remains authoritative. Existing command envelopes, receipts, quotas and domain errors are unchanged.

| RPC | Input and result |
| --- | --- |
| `save_maintenance_plan(ctx,fields)` | `ctx={organization_id,request_id,expected_version?}`. Full fields: optional `id` for edit; `asset_id,title,instructions,category,cadence,frequency,anchor_on,supervisor_id,assignee_ids,checklist,status`. Returns the ordinary `{data:MaintenancePlan,version,request_id}`. Create omits `id`/expected version; every edit requires the current positive version. |
| `preview_maintenance_plan(organization_id,fields)` | Same full fields. Read-only result includes current plan/version, server evaluation instant, old/new local dates, protected cutoff, target timezone, `local_day_end` policy, first new date/zone/UTC cutoff, up to 100 protected backlog segment summaries and `backlog_has_more`, plus proposed personnel eligibility. No writes, receipts, cursor advances or invented jobs. |
| `list_maintenance_plans(organization_id,cursor?,page_size=25)` | Stable ascending UUID cursor, maximum 100 rows, `{items,next_cursor}`. Coordinators see their tenant; technicians see only plans currently assigned to them. Inventory/nonmembers/revoked accounts are denied. |
| `list_maintenance_revisions(organization_id,plan_id,cursor?,page_size=25)` | Stable ascending positive revision cursor, maximum 100 rows. `{items:[{revision,segment}],next_cursor}` retains original author, personnel, content, calendar/zone and cursor/boundary. Same current access check on every page. |

`cadence` is day/week/month; frequency is an integer 1–365. The date is an anchored local calendar day. Day/week calculations use date arithmetic; month calculations always start from the original anchor, so January 31 → leap February 29 → March 31. Input dates use four-digit Common Era years 0001–9999; December 31, 9999 is excluded because its following-midnight cutoff cannot use that representation. A computed date beyond the supported range returns `VALIDATION` and preserves state. Personnel are unique (1–30) and currently active eligible tenant members; checklist has 1–100 nonblank items. Author, timezone, due instant, system actor and authorization cannot be supplied by clients. The organization supplies the current IANA timezone.

The exclusive UTC cutoff is `((scheduled_local_date+1)::timestamp AT TIME ZONE pinned_timezone)`, evaluated by PostgreSQL. Literal SQL fixtures cover month-end/leap, normal DST and nonexistent/repeated midnight, including the Apia date-line change. Client timezone never determines this instant. Preview is advisory at its returned server instant; save recalculates under the organization/asset/plan locks using one current server instant. Consumers should refresh stale previews and display saved revision details. No browser-selected clock parameter is exposed.

On an edit, protect dates through the greatest of the old-zone local date, proposed-zone local date and earlier protected boundaries. Only the formerly open segment receives this boundary. Its original `next_ordinal` stays unchanged; all earlier protected segments stay unchanged. The new revision's first date is strictly after the cutoff. Creation may intentionally start in the past, yielding retained backlog. Preview returns segment summaries rather than eagerly enumerating every missed date; `backlog_has_more` is not a total count and does not authorize dropping omitted segments. Paginated revision reads expose remaining segments. Pause/archive add history and prevent dependent generation; they never delete backlog or cancel work.

Historical revision author/content/personnel and current generation authorization are distinct facts. Every save is a new explicit coordinator authorization: `maintenance_plans.authorized_by` and `current_revision_id` identify the current authorizer/supervisor/assignees. `private.maintenance_current_people_eligible(org,plan)` checks that current set, including active Auth accounts. POR-30 must use those current personnel for **every** retained segment, while sourcing instructions/checklist/cadence/zone/date from the segment's historical revision. It must not also require revoked historical personnel or rewrite their historical facts. An invalid current set blocks generation without advancing a cursor; an explicit valid replacement can unblock retained dates. Exact-once generation and its occurrence provenance remain POR-30 checks, not an acceptance claim of this slice.

All new tables enable RLS and deny direct access to anon/authenticated/service-role clients. Only authenticated named RPC execution is granted; definer functions use an empty search path and recheck current account/tenant/role. Plan save serializes on organization, then asset, then plan; POR-30 must preserve that ordering with its work-order locks. Replays require current coordinator authority, return the original receipt and do not revalidate old personnel as a new authorization. Changed payloads conflict, including changed expected versions. After an uncertain acknowledgement, preserve the caller's request identity and exact payload; do not mint a fresh retry. New saves validate all fields and current personnel before committing revision/segment/receipt/audit atomically.

Migration `20261024000100_maintenance_plans.sql` is additive and does not rewrite the retained legacy draft migration or existing operational contracts. Recovery uses forward repair, never deletion of revisions, protected segments or durable receipts.

# Maintenance plan commands and preview

POR-29 supplies plans, immutable revisions, protected date segments and bounded authorized reads. POR-30 adds the private generator, immutable occurrences, native Cron and explicit Start integration in `20261024000200_maintenance_generation.sql`. The Maintenance page remains POR-31 work. Applying the generation migration installs the native job; this source change does not apply it to a hosted environment.

The shared Zod definitions are in `supabase/functions/_shared/maintenance.ts`, re-exported by `src/contracts/maintenance.ts`; `src/app/maintenance-client.ts` owns the typed client boundary. Database authorization remains authoritative. Existing command envelopes, receipts, quotas and domain errors are unchanged.

| RPC | Input and result |
| --- | --- |
| `save_maintenance_plan(ctx,fields)` | `ctx={organization_id,request_id,expected_version?}`. Full fields: optional `id` for edit; `asset_id,title,instructions,category,cadence,frequency,anchor_on,supervisor_id,assignee_ids,checklist,status`. Returns the ordinary `{data:MaintenancePlan,version,request_id}`. Create omits `id`/expected version; every edit requires the current positive version. |
| `preview_maintenance_plan(organization_id,fields)` | Same full fields. Read-only result includes current plan/version, server evaluation instant, old/new local dates, protected cutoff, target timezone, `local_day_end` policy, first new date/zone/UTC cutoff, up to 100 protected backlog segment summaries and `backlog_has_more`, plus proposed personnel eligibility. No writes, receipts, cursor advances or invented jobs. |
| `list_maintenance_plans(organization_id,cursor?,page_size=25)` | Stable ascending UUID cursor, maximum 100 rows, `{items,next_cursor}`. Coordinators see their tenant; technicians see only plans currently assigned to them. Inventory/nonmembers/revoked accounts are denied. |
| `list_maintenance_revisions(organization_id,plan_id,cursor?,page_size=25)` | Stable ascending positive revision cursor, maximum 100 rows. `{items:[{revision,segment}],next_cursor}` retains original author, personnel, content, calendar/zone and cursor/boundary. Same current access check on every page. |
| `list_maintenance_agenda(organization_id,from_on,to_on,cursor?,page_size=25)` | Inclusive saved scheduled-date window of at most 366 days; ascending `{date,id}` cursor, maximum 100 occurrences. `{items,next_cursor}`. Each item exposes immutable occurrence ID/plan/revision/date/zone/cutoff/authorization/personnel/WO provenance plus current `work_status,blocks_operation,planned_on,title`. Both current plan and work-order access must permit the row. Date windows refer to the pinned scheduled local date, independent of browser timezone. |
| `list_maintenance_backlog(organization_id,plan_id,cursor?,page_size=25)` | Ascending revision cursor, maximum 100 pending segment summaries. Each item has `revision_id,revision,author_id,next_ordinal,next_on,protected_through,timezone,due_at`. Returns `evaluated_at,status,generation_blocked,last_checked_at,next_cursor`; it enumerates segments, never all missed dates or a fabricated total. Uses the current server time and current plan access, with no writes or cursor consumption. |

The existing plan list is the bounded blocker/status read. `generation_blocked` is the last observed generation result; use its `last_checked_at` and the backlog read's `evaluated_at`, rather than treating it as a permanent live eligibility guarantee. Paused/archived plans retain their pending segment summaries. Agenda links must still recheck work-order authorization when opened. Technician access can change immediately on reassignment/revocation; a historical assignment alone does not grant current plan access.

`cadence` is day/week/month; frequency is an integer 1–365. The date is an anchored local calendar day. Day/week calculations use date arithmetic; month calculations always start from the original anchor, so January 31 → leap February 29 → March 31. Input dates use four-digit Common Era years 0001–9999; December 31, 9999 is excluded because its following-midnight cutoff cannot use that representation. A computed date beyond the supported range returns `VALIDATION` and preserves state. Personnel are unique (1–30) and currently active eligible tenant members; checklist has 1–100 nonblank items. Author, timezone, due instant, system actor and authorization cannot be supplied by clients. The organization supplies the current IANA timezone.

The exclusive UTC cutoff is `((scheduled_local_date+1)::timestamp AT TIME ZONE pinned_timezone)`, evaluated by PostgreSQL. Literal SQL fixtures cover month-end/leap, normal DST and nonexistent/repeated midnight, including the Apia date-line change. Client timezone never determines this instant. Preview is advisory at its returned server instant; save recalculates under the organization/asset/plan locks using one current server instant. Consumers should refresh stale previews and display saved revision details. No browser-selected clock parameter is exposed.

On an edit, protect dates through the greatest of the old-zone local date, proposed-zone local date and earlier protected boundaries. Only the formerly open segment receives this boundary. Its original `next_ordinal` stays unchanged; all earlier protected segments stay unchanged. The new revision's first date is strictly after the cutoff. Creation may intentionally start in the past, yielding retained backlog. Preview returns segment summaries rather than eagerly enumerating every missed date; `backlog_has_more` is not a total count and does not authorize dropping omitted segments. Paginated revision reads expose remaining segments. Pause/archive add history and prevent dependent generation; they never delete backlog or cancel work.

Historical revision author/content/personnel and current generation authorization are distinct facts. Every save is a new explicit coordinator authorization: `maintenance_plans.authorized_by` and `current_revision_id` identify the current authorizer/supervisor/assignees. `private.maintenance_current_people_eligible(org,plan)` checks that current set, including active Auth accounts. Generation uses those current personnel for **every** retained segment, while sourcing instructions/checklist/cadence/zone/date from the segment's historical revision. It does not require revoked historical personnel or rewrite their historical facts. An invalid current set blocks generation without advancing a cursor; an explicit valid replacement can unblock retained dates. Occurrences pin the actual current authorizer/supervisor/assignees used for that execution, alongside the historical revision ID and its original author.

`private.generate_due_maintenance(at_time default now())` is a native database executor, denied to PUBLIC/anon/authenticated/service-role clients. There is no public scheduler RPC, synthetic Auth account or human command receipt for generation. The owner-installed `opspilot-maintenance` Cron job runs at minute 5 hourly. It checks at most 100 plans and creates at most 200 occurrences per call; one unfinished generated job per plan makes the current effective creation maximum 100. Overlap skips locked organizations/assets/plans. Lock order remains organization → asset → stable work-order set → plan. The unique `(plan_id,scheduled_local_date)` identity, job, checklist, assignments, notifications, audit and cursor advance commit together. A later per-plan dependency failure rolls them all back, records `dependency`, and retains the original pending date. An unavailable whole database cannot record a blocker; the persisted cursor/backlog remains the recovery source.

Both human commands and generation use the existing 5,000/day tenant budget under the same organization lock. Usage is human command receipts plus durable occurrences in the existing database-day window, based on real transaction time rather than the executor's supplied evaluation clock. Human per-minute and invitation limits remain unchanged. System generation creates a constrained `actor_kind=system,system_identity=maintenance_scheduler` audit, never a human receipt. Work orders allow a null creator only for `creation_actor_kind=system` with a valid PM occurrence source. Hold/performer/reviewer/releaser identities remain required humans. Legacy receipts retain their saved shapes; system jobs returned by assignment include their discriminator/source.

Generation creates `scheduled`, nonblocking work with `planned_on=scheduled_local_date` and the pinned due cutoff. Generation, overdue status, rescheduling and pre-Start cancellation do not refresh availability or create a hold. The existing authorized human Start, requiring a current eligible assignment, atomically changes blocking to true, creates the ordinary hold and enters In Progress. Normal immutable participants, performer attestation, evidence, review, cancel/disposition, reopen and separate eligible release then apply. A PM due-field edit is `VALIDATION`, even if the submitted value equals the stored cutoff; rescheduling `planned_on` remains supported. Start/release serialize on the existing safety locks. No path automatically marks an asset Operational.

All new tables enable RLS and deny direct access to anon/authenticated/service-role clients. Only authenticated named RPC execution is granted; definer functions use an empty search path and recheck current account/tenant/role. Plan save serializes on organization, then asset, then plan; POR-30 must preserve that ordering with its work-order locks. Replays require current coordinator authority, return the original receipt and do not revalidate old personnel as a new authorization. Changed payloads conflict, including changed expected versions. After an uncertain acknowledgement, preserve the caller's request identity and exact payload; do not mint a fresh retry. New saves validate all fields and current personnel before committing revision/segment/receipt/audit atomically.

Both maintenance migrations are additive and do not rewrite the retained legacy draft. Recovery uses authorized forward repair, never deletion of revisions, occurrences, protected segments or durable receipts. Quiesce the native job through the authorized database operator during repair/restore, reconcile restored occurrence/job/cursor and current revocations, then resume native execution; retry with the original due identity. Disabling generation leaves all human safety/release paths and pending dates intact. The populated-upgrade rehearsal exercises generation beside genuine legacy receipt replay. The backup/recovery rehearsal checks saved occurrences/jobs/cursors and receipts survive restore, reapplies revocation before access, then verifies retry cannot duplicate work or consume a blocked date. It retains exact object/default ACL assertions, extended to Cron objects. No real/private dump is published.

Validation commands: focused contract/client Vitest, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `git diff --check`; real backend `npm run db:test` and `npm run test:integration`. The existing full Linux PR-event CI retains populated upgrade, reset/native schema generation, Edge readiness, database authorization, integration, browser, recovery, exact schema comparison and unconditional owned cleanup. Windows without isolated services cannot establish SQL/Auth/upgrade/recovery evidence. Native generated types must be adopted from the migrated isolated schema and compared by final CI before acceptance. ASVS 5 Level 2 applicability, human/security/safety/private-pilot gates and the separate UI/accessibility gates remain required in their assigned phases.

Isolated CI disables the installed native job after reset/upgrade. One sequential integration scenario temporarily activates that actual postgres-owned job, verifies its durable output and successful native run, and quiesces it in `finally`. Integration files run serially because the executor operates database-wide. Ordinary scenarios otherwise retain separate tenant/user/record state; quota, concurrency, failure injection and restore fixtures intentionally share only their scenario state. Local source checks and authored SQL fixtures do not establish native execution or acceptance; unavailable checks remain unverified until the exact candidate passes the full isolated gate.

# Job-parts API and recovery (26B)

The strict shared contract is `supabase/functions/_shared/inventory.ts`, re-exported by `src/contracts/inventory.ts` and consumed by `src/app/inventory-client.ts`. All five commands use `(ctx,fields)` with mandatory positive `ctx.expected_version` for the current work order. `fields` is `{work_order_id,lines}`; 1–100 distinct lines commit atomically. Quantities are positive decimal strings, exact to `numeric(14,3)`, without rounding. Duplicate part IDs (request), part/location pairs (reserve), or reservation IDs (release/issue/return) are rejected. Each work order holds at most 100 requested parts and 100 part/location reservations so its complete read stays bounded.

| Command / client | Current authority | Line fields and effect |
| --- | --- | --- |
| `request_parts` / `requestParts` | Assigned technician only | `part_id,quantity,unit`; adds demand without moving/reserving stock. |
| `reserve_parts` / `reserveParts` | Owner, manager, supervisor, inventory | `part_id,location_id,quantity,unit`; reserves requested demand against available stock. |
| `release_reservation` / `releaseReservation` | Owner, manager, supervisor, inventory | `reservation_id,quantity,unit`; releases unused reserved quantity. |
| `issue_reserved_stock` / `issueReservedStock` | Owner, inventory | `reservation_id,quantity,unit`; partially or fully issues stock, reducing reserved and on-hand once. |
| `return_stock` / `returnStock` | Owner, inventory | `reservation_id,quantity,unit`; increases on-hand, bounded by issued minus returned, including after cancellation/completion/archive. |

Reservation IDs remain stable per job/part/location. Releasing and later reserving the same pair retains cumulative issued/returned/released history. Reservation admission cannot exceed unfulfilled requested quantity. Fresh request/reserve/release/issue commands reject completed/canceled jobs and archived assets; request/reserve also reject archived parts. No command starts/resumes work, completes a repair, clears a hold, or repeats consumption on reopen. The authoritative cancellation transition atomically releases only unused reservations. Invalid cancellation leaves reservations intact.

Duplicate detection compares UUID identity, including case variants, at both shared schema and direct SQL boundaries; it preserves original command fields for replay. Legacy `adjust_stock` linked compensation rejects `issue` and `return` predecessors with `INVALID_TRANSITION`: job stock comes back through `return_stock`, bounded by net issued quantity. A mistaken return cannot be reversed by legacy compensation. Receipt/adjustment linked reversals retain their AAL2 requirement, exact opposite quantity, one-reversal limit and durable replay.

`get_job_parts(organization_id,work_order_id)` / `getJobParts` returns `{id,number,status,version,parts,reservations,reconciliation_state}`. Each part has `{part_id,unit,requested,reserved,issued,returned,shortage}`; shortage is `max(0,requested-reserved-issued+returned)`. Each reservation has `{id,part_id,location_id,unit,reserved,issued,returned,released}`. All quantities are strings. No people, repair notes, attachments, or unrelated stock rows are returned. Current owner/manager/supervisor/inventory members and currently assigned technicians may read. `reconciliation_state` is `consistent` or `discrepancy`, comparing linked stock ledger and aggregate unused reservations. Discrepancy blocking and shortage notifications belong to 26C; inventory UI belongs to 26D.

Commands acquire tenant admission, asset, work-order, sorted part and part/location stock locks. New commands require current WO version and increment it once. Membership/role/assignment is rechecked before replay. An uncertain acknowledgement must retain the original request ID, fields and expected version; authorized replay returns the old envelope before its stale version is checked. Changed payload/action conflicts; removed membership/assignment cannot retrieve an old result. Failed multi-line commands roll back stock, allocations, WO version, audit and receipt together. Existing quotas and domain errors apply.

The additive `20261024000600_job_parts.sql` adds `work_order_parts`, `stock_reservations` and immutable `job_stock_movements` links. Existing movement columns, receipt/adjustment responses and old receipt hashes stay unchanged. `kind` additionally permits `issue` and `return`; legacy movement request uniqueness is a partial index, while new movement links enforce one reservation movement per request. Direct tables/private helpers remain revoked from API roles including service-role, with RLS enabled/forced. Public user commands grant execute only to authenticated users; credentials are never arguments or part of fields.

Recover forward from an authorized consistent snapshot, preserving all three new tables, movements, balances, current access decisions, receipts and audit. Verify `on_hand = signed ledger sum`, `reserved = sum(quantity-issued-released)` across reservations and `available = on_hand-reserved`; verify job reads and original command replay without another movement. Reconcile revoked identities before enabling access. Do not delete receipts/history, reconstruct stock by destructive edits, or apply a destructive down migration. A transaction error rolls back automatically. A migration failure requires diagnosis and an authorized forward fix; no hosted migration or restore is implied.

Required verification is the final full PR CI: populated 26A upgrade, reset, native generated types comparison, SQL authorization/security, Edge, real service multi-line/20-contender/retry/return/cancel tests, existing WO regressions, browser journey, restored job allocations/issue/return and unconditional owned cleanup. Local type/lint/unit/build checks cannot verify PostgreSQL or Auth. Native types are provisional until CI comparison. ASVS 5 Level 2 applicability, qualified human/security and inventory business-process/private-pilot gates remain separate from synthetic review and acceptance.

The additive 26C guardrails are documented in [inventory-guardrails.md](inventory-guardrails.md). They preserve this frozen command/read shape while adding authoritative discrepancy blocking, per-location low-stock cycles and explicit shortage recovery.
